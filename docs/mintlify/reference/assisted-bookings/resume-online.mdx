# Reprendre le paiement en ligne

Arbitre contre une éventuelle prise en charge agence : l'opération n'est valide que tant que le dossier est `pending`. Le devis est recalculé et les sièges sont réacquis **atomiquement** sur le même itinéraire et les mêmes départs — la première opération validée gagne, l'autre reçoit un conflit `409`. Aucune nouvelle réservation n'est créée.

## Paramètres

<ParamField path="reservation_uuid" type="UUID" required>
  UUID de la réservation (route model binding sur colonne `uuid`).
</ParamField>

<ParamField body="idempotency_key" type="string" required>
  Clé d'idempotence générée par le client.
</ParamField>

<ParamField body="passengers" type="array" required>
  Affectations de sièges par passager : `passenger_index` puis `seat_assignments` (`leg_order` + `seat_uuid`) pour chaque jambe.
</ParamField>

## Codes de réponse

| Code | Description |
|------|-------------|
| `200` | Reprise réussie : devis recalculé, sièges bloqués, réservation `held`. |
| `401` | Token absent ou invalide. |
| `403` | Réservation appartenant à un autre utilisateur. |
| `409` | Dossier déjà pris en charge par un agent, ou siège demandé devenu indisponible (`seat_code` retourné). |
| `422` | Payload invalide ou dossier expiré/indisponible. |

<Warning>
  En cas de conflit de siège (`409`), renvoyer le voyageur vers la sélection des sièges en utilisant `conflicting_seat_uuid` / `seat_code` — aucune réservation supplémentaire n'est créée. Un changement de trajet impose une nouvelle réservation.
</Warning>
