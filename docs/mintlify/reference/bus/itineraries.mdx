# Rechercher des itinéraires

Endpoint public et canonique de recherche mobile. Un résultat contient un ou plusieurs `legs`. Un trajet direct est représenté par une liste contenant un seul leg.

Chaque leg expose des données riches — ligne, véhicule avec amenities, arrêts d'origine et de destination avec ville et pays, classe de service, nombre de sièges disponibles — pour que le mobile puisse afficher les résultats sans appels supplémentaires.

## Aller simple vs aller-retour

- **Aller simple** (`trip_type=one_way`, défaut) : la réponse utilise la clé `data`.
- **Aller-retour avec date de retour** (`trip_type=round_trip` + `return_date`) : la réponse utilise deux clés `outbound` et `inbound`. Le retour recherche sur la date spécifiée, depuis la destination vers l'origine.
- **Aller-retour sans date de retour** (`trip_type=round_trip` sans `return_date`) : la réponse utilise deux clés `outbound` et `inbound`. Le retour recherche les prochains départs disponibles sur `default_search_days` (7 jours par défaut) à partir du lendemain du départ. Le mobile peut ainsi proposer une liste de retours disponibles sans que l'utilisateur choisisse une date précise.

## Paramètres

<ParamField query="from_physical_stop_uuid" type="UUID" required>
  UUID du point physique d'origine.
</ParamField>

<ParamField query="to_physical_stop_uuid" type="UUID" required>
  UUID du point physique de destination.
</ParamField>

<ParamField query="date" type="string" required>
  Date de départ au format `Y-m-d`.
</ParamField>

<ParamField query="passenger_count" type="integer">
  Nombre de passagers. Défaut : `1`. Maximum autorisé par les paramètres de réservation de groupe.
</ParamField>

<ParamField query="trip_type" type="string">
  Type de trajet : `one_way` ou `round_trip`. Défaut : `one_way`. Quand `round_trip`, `return_date` est requis et la réponse change de shape (`{ outbound, inbound }` au lieu de `{ data }`).
</ParamField>

<ParamField query="return_date" type="string">
  Date de retour au format `Y-m-d`. Optionnel quand `trip_type=round_trip` : si absent, la recherche retour scanne les 7 prochains jours à partir du lendemain du départ.
</ParamField>

<ParamField query="sort" type="string">
  Clé de tri : `departure_time`, `arrival_time`, `price`, `duration`, `connections`. Défaut : `connections` (trajets directs en premier).
</ParamField>

<ParamField query="sort_direction" type="string">
  Direction du tri : `asc` ou `desc`. Défaut : `asc`.
</ParamField>

<ParamField query="service_class_code" type="string">
  Code de classe de service pour filtrer les résultats (ex. `confort`, `premium`). Doit exister dans `service_classes`.
</ParamField>

## Règles

- Les points physiques sont identifiés par UUID ; un libellé de ville ne suffit pas pour poursuivre la réservation.
- `leg_order` commence à `1`.
- `connections_count` vaut `0` pour un trajet direct, `>0` pour un trajet avec correspondances.
- Le tri secondaire est stable : à valeur de tri égale, les directs sont prioritaires, puis tri par `departure_at`.
- Le filtre `service_class_code` ne retient que les itinéraires dont au moins une leg propose cette classe.
- Pour l'aller-retour, la recherche inbound inverse automatiquement l'origine et la destination.
- Le prix retourné est un aperçu de recherche. Créez un devis d'itinéraire avant de l'afficher comme prix contractuel.
- La réponse est publique et ne contient aucune donnée de réservation ou de passager.

## Codes de réponse

| Code | Description |
|---|---|
| `200` | Itinéraires trouvés ou liste vide. |
| `422` | Point physique, date, paramètre de tri, classe de service ou `trip_type` invalide. |
| `429` | Limite de recherche atteinte. |
