# Vérifier explicitement un paiement

Cet endpoint est appelé par l'application mobile lorsqu'elle veut demander une vérification immédiate côté serveur. Le serveur interroge l'endpoint officiel du provider (`FedaPay::retrieve` ou `MTN MoMo requesttopay/{reference}`), met à jour le statut local du paiement, puis retourne la ressource complète.

Si le paiement est déjà dans un statut terminal (`confirmed`, `failed`, `cancelled`, `refunded`), le serveur retourne l'état existant **sans** rappeler le provider.

<Warning>
  La vérification explicite **ne remplace pas** le webhook provider. Elle permet au mobile de provoquer une synchronisation sans attendre le webhook. Le polling `GET /payments/{uuid}` reste utile pour rafraîchir l'état entre deux vérifications.
</Warning>

## Paramètres

<ParamField path="payment_uuid" type="UUID" required>
  UUID du paiement (route model binding sur colonne `uuid`).
</ParamField>

Aucun corps de requête.

## Réponse

La réponse reprend `PaymentResource` (même structure que `GET /payments/{uuid}`).

<ResponseField name="data" type="Payment" required>
  <ResponseField name="uuid" type="UUID" required>UUID du paiement.</ResponseField>
  <ResponseField name="status" type="string" required>`pending`, `confirmed`, `failed`, `cancelled`, ou `refunded`.</ResponseField>
  <ResponseField name="next_action" type="string" required>Action attendue : `verify` (toujours pending), `wait_for_tickets` (confirmed, billets en cours), `show_tickets` (confirmed, billets émis), `retry` (failed/cancelled).</ResponseField>
  <ResponseField name="last_verified_at" type="string">Horodatage de cette vérification (ISO 8601).</ResponseField>
  <ResponseField name="provider_reference" type="string">Référence provider ou `null`.</ResponseField>
  <ResponseField name="provider_transaction_id" type="string">ID technique provider ou `null`.</ResponseField>
  <ResponseField name="confirmed_at" type="string">Date de confirmation (ISO 8601) ou `null`.</ResponseField>
  <ResponseField name="failure" type="object">Présent si échec. Contient `code` et `message`.</ResponseField>
  <ResponseField name="reservation" type="object" required>Relation chargée avec `ticket_issuance`.</ResponseField>
  <ResponseField name="reservation.ticket_issuance.status" type="string" required>`not_started`, `pending`, `processing`, `issued`, ou `failed`.</ResponseField>
  <ResponseField name="reservation.ticket_issuance.tickets_url" type="string" required>URL vers les billets.</ResponseField>
</ResponseField>

## Codes de réponse

| Code | Description |
|------|-------------|
| `200` | État provider vérifié ou état terminal déjà connu. |
| `401` | Session absente ou invalide. |
| `403` | Le paiement appartient à un autre passager. |
| `404` | Paiement introuvable. |
| `429` | Trop de vérifications rapprochées — respecter le délai de 10 secondes (rate limit `payment-verify`: 6/min). |

<Info>
  Après `confirmed`, l'émission des billets est traitée par un job asynchrone. Le mobile attend `next_action=show_tickets`, puis appelle `GET /api/v1/bookings/{reservation_uuid}/tickets`.
</Info>
