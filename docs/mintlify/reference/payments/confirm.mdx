# Confirmer un paiement (webhook)

Endpoint appelé par le **provider de paiement** (Mobile Money, carte) pour confirmer ou échouer un paiement. Cet endpoint est **public** — la sécurité repose sur l'isolation réseau et/ou une signature provider (roadmap).

<Warning>
  L'app mobile **n'appelle jamais** cet endpoint. Elle utilise `POST /payments/{uuid}/verify`, puis `GET /payments/{uuid}` pour rafraîchir l'état.
</Warning>

## Paramètres

<ParamField path="payment_uuid" type="UUID" required>
  UUID du paiement (route model binding sur colonne `uuid`).
</ParamField>

<ParamField body="status" type="string" required>
  `success`, `confirmed`, ou `failed`.
</ParamField>

<ParamField body="provider_reference" type="string">
  Référence provider (ex: `MM-98270341`). Max 255.
</ParamField>

<ParamField body="provider_payload" type="object">
  Payload brut du provider pour audit (tableau associatif).
</ParamField>

## Réponse

<ResponseField name="status" type="string" required>
  Statut final du paiement : `pending`, `confirmed`, `failed`, `cancelled`, ou `refunded`.
</ResponseField>
<ResponseField name="payment_uuid" type="UUID" required>
  UUID du paiement confirmé.
</ResponseField>
<ResponseField name="reservation_uuid" type="UUID">
  UUID de la réservation associée ou `null`.
</ResponseField>
<ResponseField name="reservation_status" type="string">
  Statut final de la réservation (`held`, `confirmed`, `paid`, `ticketed`, `boarded`, `cancelled`, `expired`) ou `null`.
</ResponseField>

## Effets sur la réservation

| `status` webhook | Réservation | Paiement | Billet |
|------------------|-------------|----------|--------|
| `success` / `confirmed` | `held` → `paid` | `pending` → `confirmed` | Émis ensuite par un job asynchrone |
| `failed` | reste `held` (jusqu'à expiration) | `pending` → `failed` | Non émis |

## Codes de réponse

| Code | Description |
|------|-------------|
| `200` | Paiement confirmé ou échoué — statut retourné. |
| `422` | `status` invalide ou validation échouée. |
| `404` | Paiement introuvable. |

<Warning>
  Si le webhook arrive **après l'expiration** du hold, le backend conserve la réservation à `expired`, libère les segments et marque le paiement `failed`. Une réservation expirée n'est **jamais** réactivée.
</Warning>

<Note>
  **Sécurité** : Une signature HMAC provider est prévue en roadmap. En attendant, l'isolation réseau (VPN, IP allowlist) protège l'endpoint en production.
</Note>
