# Cycle de vie d'un paiement

Le paiement KORA BUS suit un cycle asynchrone : **catalogue** → **initiation** → **vérification serveur** → **confirmation locale** → **émission asynchrone des billets**. Le polling sert à rafraîchir l'état; il ne remplace pas la vérification explicite.

## Vue d'ensemble

```
methods → initiate → pending → verify → confirmed / failed
                                      ↓
                    reservation: held → paid
                                      ↓
                         ticket issuance: pending → issued
```

<Steps>
  <Step title="1. Initier le paiement">
    La réservation doit être au statut `held`. Fournissez une `idempotency_key` unique.

```bash
curl -X POST https://staging.koraexpress.app/api/v1/payments/initiate \
  -H 'Authorization: Bearer $TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{
    "reservation_uuid": "9b1deb4d-...",
    "method": "mobile_money",
    "provider": "mtn_momo",
    "idempotency_key": "pay-2026-08-20-001",
    "phone": "+2290197421860",
    "mobile_money_network": "mtn_momo"
  }'
```

La réponse `201` contient le `uuid` du paiement, le statut `pending`, et `polling_interval_seconds` (10s).

Voir : [Initier — Référence](/reference/payments/initiate).
  </Step>

  <Step title="2. Vérifier côté serveur puis rafraîchir">
    Appelez `POST /payments/{uuid}/verify` après l'approbation du client. Le serveur interroge l'endpoint officiel du provider, puis l'application peut rafraîchir avec `GET /payments/{uuid}` toutes les `polling_interval_seconds` secondes.

```dart
Timer.periodic(Duration(seconds: 10), (timer) async {
  final res = await authDio.get('/api/v1/payments/$paymentUuid');
  final status = res.data['data']['status'];

  if (status == 'confirmed' && data['data']['next_action'] == 'show_tickets') {
    timer.cancel();
    // Appeler GET /bookings/{reservationUuid}/tickets
  } else if (status == 'failed') {
    timer.cancel();
    // Afficher l'erreur
  }
});
```

Voir : [Consulter — Référence](/reference/payments/show).
  </Step>

  <Step title="3. Attendre l'émission du billet">
    Après `confirmed`, la réservation passe à `paid` et l'émission des billets est réalisée par un job idempotent. Consultez `reservation.ticket_issuance.status`; une erreur d'émission peut être relancée sans débiter à nouveau le passager.

    - `confirmed` + `issued` → afficher les billets
    - `confirmed` + `pending|processing` → afficher l'attente
    - `failed` → proposer une nouvelle tentative

    L'app mobile n'appelle **pas** cet endpoint — c'est le provider qui le fait.

Voir : [Confirmer — Référence](/reference/payments/confirm).
  </Step>
</Steps>

## Méthodes de paiement

| Méthode | `method` | Providers configurables au Bénin | Champ requis |
|---------|----------|-------------------|--------------|
| Mobile Money | `mobile_money` | `fedapay`, `mtn_momo` | `phone`, `mobile_money_network` |
| Mini Wallet | `wallet` | Hors MVP | — |

Les réservations KORA restent en XOF. MTN utilise EUR uniquement dans le sandbox public; le montant numérique de test est transmis tel quel. En production, la devise doit correspondre au compte MTN provisionné.

## Idempotence

La `idempotency_key` garantit qu'un replay de la même demande ne crée pas un double paiement :

- **Premier appel** → `201` (paiement créé)
- **Replay même clé** → `200` (paiement existant retourné)

<Info>
  Utilisez une clé déterministe côté mobile (ex: `pay-{reservation_uuid}-{timestamp}`) pour survivre aux retries réseau sans double paiement.
</Info>

## Cas d'erreur

| Situation | Code | Action |
|-----------|------|--------|
| Réservation non `held` | `422` | Vérifier le statut via `GET /bookings/{uuid}` |
| Hold expiré avant initiation | `422` | Recréer un devis + hold |
| Webhook succès après expiration | — | Paiement `failed`, réservation reste `expired` |
| Provider timeout | — | Continuer à poller ; le webhook finira par arriver |

<Warning>
  Le paiement est accepté **uniquement** tant que le hold est valide. Si le webhook de succès arrive après l'expiration, le backend marque le paiement `failed` et ne réactive **jamais** la réservation. Le passager doit recommencer une nouvelle recherche.
</Warning>
