# Webhooks

KORA BUS utilise un webhook pour confirmer le statut d'un paiement côté serveur. Le provider de paiement (Mobile Money, carte) appelle l'API KORA après traitement de la transaction.

## Endpoint de confirmation

`POST /api/v1/payments/{payment_uuid}/confirm`

Cet endpoint est **public** (`@unauthenticated`) — il est appelé par le provider, pas par l'app mobile.

<Warning>
  L'app mobile **n'appelle jamais** cet endpoint. Elle polle le statut via `GET /payments/{uuid}` ou attend une notification push.
</Warning>

## Payload du webhook

```json
{
  "status": "success",
  "provider_reference": "MM-98270341",
  "provider_payload": {
    "transaction_id": "TXN-12345",
    "amount": 12500,
    "currency": "XOF"
  }
}
```

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `status` | string | ✅ | `success`, `confirmed`, ou `failed`. |
| `provider_reference` | string | ❌ | Référence provider. |
| `provider_payload` | object | ❌ | Payload brut pour audit. |

## Réponse du webhook

```json
{
  "status": "confirmed",
  "payment_uuid": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb80",
  "reservation_uuid": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb70",
  "reservation_status": "paid"
}
```

## Effets sur la réservation

| `status` webhook | Réservation | Paiement | Billet |
|------------------|-------------|----------|--------|
| `success` / `confirmed` | `held` → `paid` | `pending` → `confirmed` | Émis (fiscalisation MECeF) |
| `failed` | reste `held` (jusqu'à expiration) | `pending` → `failed` | Non émis |

## Webhook tardif (après expiration)

<Steps>
  <Step title="Scénario">
    Le passager initie un paiement. Le hold expire avant que le provider ne confirme. Le webhook de succès arrive ensuite.
  </Step>
  <Step title="Comportement backend">
    Le backend conserve la réservation à `expired`, libère les segments, et marque le paiement `failed` avec `provider_payload.rejection_reason = reservation_expired`.
  </Step>
  <Step title="Conséquence">
    La réservation n'est **jamais** réactivée. Le passager doit recommencer une nouvelle recherche. Le remboursement (le cas échéant) est géré hors API par le provider.
  </Step>
</Steps>

## Sécurité

<Note>
  **État actuel** : L'endpoint de confirmation est public. La sécurité repose sur l'isolation réseau (VPN, IP allowlist du provider) en production.
</Note>

<Info>
  **Roadmap** : Une signature HMAC sera ajoutée pour authentifier les webhooks. Le header `X-Kora-Signature` contiendra le HMAC-SHA256 du payload, calculé avec un secret partagé entre KORA et le provider. Le backend vérifiera la signature avant de traiter le webhook.
</Info>

## Recommandations d'intégration

1. **Ne pas logger** le `provider_payload` en clair côté client — il peut contenir des références sensibles.
2. **Poller avec backoff** : commencez à 10s, augmentez progressivement (10s, 15s, 30s) pour éviter de saturer l'API.
3. **Timeout côté mobile** : après 5 minutes sans statut terminal, proposez au passager de vérifier manuellement ou de contacter le support.
4. **Push notifications** : le backend peut envoyer une notification push (`push_token` enregistré à l'authentification) quand le paiement est confirmé, pour éviter un polling prolongé.
